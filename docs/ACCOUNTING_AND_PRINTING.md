# شاشات الحسابات والفاتورة والطباعة

التنفيذ داخل elnotaapp فقط. لا تغييرات في الموقع أو قاعدة الإنتاج، ولا تفعيل للمزامنة السحابية المؤجلة. لم تتغير pubspec.yaml أو pubspec.lock ولم تُضف مكتبات.

## الشاشات

- الرئيسية: عدد العملاء، إجمالي المستحق، المحصل، تحصيل اليوم، أحدث الفواتير والحسابات الأعلى مديونية، وروابط إنشاء عميل/فاتورة/دفعة.
- العملاء: بحث بالاسم والهاتف والعنوان، تصنيف مستحق/مسدد/رصيد مقدم، وترتيب بالاسم أو المديونية. حساب العميل يعرض بياناته وإجمالياته وتبويبي الفواتير والمدفوعات. تسجيل الدفعة يظهر مرة واحدة على مستوى الحساب.
- الفواتير: قائمة عامة ببحث ورقم الفاتورة والعميل والتاريخ والصافي والحالة، مع تصفية بالتاريخ والحالة. الإنشاء يدعم مبلغًا يدويًا أو أصنافًا، خصمًا، تاريخًا، استحقاقًا وملاحظات؛ ثم ينتقل لمعاينة الفاتورة المحفوظة.
- المدفوعات: قائمة عامة مع البحث والتاريخ والإجمالي، وتفاصيل الدفعة ورابط حساب صاحبها. النموذج يحتفظ بالقيم عند الخطأ ويمنع تكرار الإرسال، ويعرض رصيد الحساب بعد الدفعة مع الحفاظ على دعم الرصيد المقدم القائم.
- الإعدادات: اسم النشاط والهاتف والعنوان للفاتورة؛ الحفظ محلي داخل transaction مع outbox.

القراءة من AccountingRepository عبر projection متسق داخل transaction. الـDAO يبث تغييرات بعد الحفظ؛ استبدلت مراقبة SQL الخام التي لم تكن تعرف table dependencies، حتى تتحدث الشاشات المفتوحة دون إعادة تشغيلها. لكل repository workspace صريح للقراءات والكتابة؛ ربط جلسات المستخدمين بالـworkspace ما زال ضمن مهمة الدمج اللاحقة.

## سلامة الحسابات

إنشاء الفاتورة وبنودها وترحيلها للـledger والـoutbox أصبح عملية محلية واحدة. فشل أي خطوة يرجع العملية كلها. التحقق يطابق إجمالي الأصناف والمبلغ والخصم ويتأكد من العميل قبل الكتابة. مفتاح الدفعة ثابت خلال المحاولة، ويُراجع داخل نفس transaction، فلا تنشأ دفعة مكررة عند إعادة الإرسال.

المبالغ قروش صحيحة. الإدخال يقبل أرقامًا عربية ويفصل الكسور بخانتين، ويرفض قص الكسور أو تحويل نص غير صالح إلى صفر. تم تصحيح اتجاه adjustments الموقّعة طبقًا لـBUSINESS_RULES: الموجب يزيد المديونية والسالب يخفضها. المبالغ التاريخية نفسها لم تُعدّل. لا حذف لعميل له ledger، ولا زر دفعة على الفواتير.

## معاينة الفاتورة

InvoiceReceipt هو مصدر العرض والصورة والطباعة، بخلفية بيضاء ثابتة حتى في الوضع الداكن. يحتوي اسم النشاط ووسائل الاتصال، رقم الفاتورة، العميل والتاريخ والاستحقاق والحالة والبنود والخصم والصافي والملاحظات. رصيد الحساب الحالي مُسمّى بوضوح ومنفصل عن صافي الفاتورة؛ لا نوزع دفعات العميل على الفواتير افتراضيًا.

التصدير PNG عبر RepaintBoundary. حفظ الصورة يفتح مكان حفظ من منتقي الملفات، ولا يفترض إضافتها تلقائيًا لألبوم الصور. المشاركة تفتح قائمة النظام بصورة image/png: يختار المستخدم WhatsApp أو تطبيقًا آخر بنفسه، ولا يُرسل شيء تلقائيًا. أجهزة iPad تحصل على sharePositionOrigin. الأنظمة التي لا تدعم مشاركة الملفات يمكنها استخدام حفظ الصورة.

الطباعة عبر النظام تحول نفس الصورة إلى PDF بمقاس A4 أو 58/80 مم، فيظل تشكيل العربي مطابقًا للمعاينة دون تنزيل خطوط أثناء الطباعة. يتم تقسيم الصورة الطويلة إلى صفحات عند طباعة A4. الصور شديدة الطول لها حد أبعاد معلن برسالة خطأ؛ لا تُحذف بنود من الصورة بصمت.

## الطابعات

| الطريقة | المنصات | نطاق الدعم |
|---|---|---|
| System print | Android / Windows / iOS وغيرها حسب printing | طابعة متاحة للنظام بتعريف مناسب؛ يشمل طابعات USB أو الشبكة أو البلوتوث التي يعرضها النظام |
| Bluetooth مباشر | Android | Bluetooth Classic SPP بطابعات ESC/POS المتوافقة، بعد الاقتران في إعدادات الهاتف |
| BLE أو SDK خاص | غير منفذ | يحتاج محولًا خاصًا بموديل الطابعة؛ لا ندّعي دعم كل طابعة بلوتوث |
| iOS Bluetooth Classic SPP مباشر | غير منفذ | يستخدم المستخدم system print؛ مسار Android لا يعمل على iOS |

مسار Android يستخدم MethodChannel وكود Kotlin أصلي، ولا يضيف dependency. يطلب BLUETOOTH_CONNECT عند الحاجة على Android 12+، ويقرأ الأجهزة المقترنة فقط دون scan أو location permission. الإذن القديم BLUETOOTH محدود إلى API 30، والطابعة اختيارية ولا تمنع تثبيت التطبيق على جهاز بدون بلوتوث.

نرسم العربي أولًا في Flutter ثم نحول RGBA إلى raster ESC/POS؛ لا نعتمد على codepage عربي داخل الطابعة. 58 مم = 384 نقطة، 80 مم = 576 نقطة؛ يجب مطابقة عرض الطباعة الفعلي في موديل الطابعة. قد تتطلب طابعة 80 مم بعرض مختلف إعدادًا إضافيًا مستقبلًا. أمر GS v 0 مدعوم في طابعات إيصالات كثيرة لكنه ليس ضمان توافق مع كل موديل. القص اختياري ومتوقف افتراضيًا. ترسل البيانات في bands من 128 صفًا وبحزم محدودة، مع مهلة اتصال/إرسال 35 ثانية وإغلاق socket عند الانتهاء. لا توجد إعادة طباعة تلقائية بعد فشل الإرسال، لأنه قد يكون طُبع جزء بالفعل.

مصادر التنفيذ: Android Bluetooth permissions/connection documentation، وEpson ESC/POS GS v 0 command reference، وواجهات المكتبات المثبتة. نجاح write إلى socket يعني إرسال البيانات، ولا يثبت خروج الورقة فعليًا. قبول موديل طابعة يحتاج اختبارًا فعليًا للوصل/فصل البلوتوث، نفاد الورق، عرض 58/80 مم والعربي.

## التحقق

- scripts/verify_web_alignment.py يبقى للتحقق من توافق المخطط وعدم المساس ببيانات v1.
- accounting_workflows_test.dart يغطي إنشاء عدة فواتير وخصم ودفعة واحدة، إعادة المحاولة، rollback كامل بفشل ledger متعمد، عزل workspace، التحديث الحي، advances/adjustments، تحليل المبالغ وbytes الطباعة.
- accounting_ui_test.dart يعرض الشاشات على 320/390/768/1440، يفحص overflow، معاينة الفاتورة وعمل دفعة واحد، ويجرب PNG/PDF/ESC-POS من نفس الرسم.
- GitHub Actions يُشغل analyzer والاختبارات على Flutter 3.44.4 مع قفل الاعتماديات، ويحفظ screenshots ضمن accounting-ui-previews عند تفعيل ELNOTA_SCREENSHOTS.
- jobs لبناء Android debug وWindows debug. النتائج المعتمدة تُسجّل في وصف PR بعد اكتمال التشغيل؛ وجود job لا يعني نجاح بناء أو اختبار جهاز.
- لا تجربة طابعة فعلية في بيئة التنفيذ، ولا إصدار موقع/تطبيق إنتاج موقّع ضمن هذه المهمة. Android debug يستخدم إعداد التوقيع التجريبي الموجود أصلًا.
